## Краткая суть исследования

**Гипотеза.** Открытая компактная VLM (≤2B параметров), дообученная методом LoRA на датасете, ориентированном на паттерны реального e2e-тестирования веб-интерфейсов, достигает в production-сценарии (end-to-end запуск через LLM-агента) качества, **сопоставимого как у базовых открытых, так и проприетарных моделей**, при стоимости одного запроса на порядок ниже.

**Метод.** Двухуровневая валидация:
1. **End-to-end через [Magnitude](https://magnitude.run)** — 50 реальных тестов на ~25 публичных сайтах (GitHub, Etsy, Wikipedia, Booking и др.) с Claude Sonnet 4.6 в роли LLM-агента, замер pass rate.
2. **Offline grounding** на held-out тест-сплите датасета `Khabner/moondream-data` (1869 примеров) и стандартных бенчмарках ScreenSpot-V2, WebClick — для калибровки и сравнения с литературой.

Дообучены две архитектуры: Moondream2 (1.86B) и Florence-2 (232M, 770M).

**Главный итог. Гипотеза подтверждена в production-сценарии:**
- **Moondream2 + LoRA v12 — 96% pass rate** на Magnitude e2e (48/50), median 52.2 с/тест. Лучший результат из 7 протестированных вариантов.
- **Moondream2 base — 88%** (44/50). LoRA даёт **+8 п.п.** на реальном e2e за счёт category-targeted доработок (HEADING/CHECKBOX/LABEL/BUTTON).
- **Florence-2-base + LoRA v1 — 84%** (42/50) при **232M параметров** — сравнимый уровень с Moondream2-base 1.86B (88%) при ×8 меньшем числе параметров.
- **Стоимость**: **~0.017 ₽ за grounding-запрос на бюджетной NVIDIA A2** (эмпирически замерено, см. §6.1) против ~0.20 ₽ за GPT-4o через российского посредника — **×12 экономия** на grounding-этапе (vs Claude/Gemini — ×18–19). Окупаемость коммерческой адаптации — 4–7 месяцев при 100 000 запросов/мес (см. §6.3).

**Критическая методологическая находка:** оптимизация моделей под стандартные grounding-бенчмарки (ScreenSpot-V2 / WebClick) **может ухудшить качество в реальном e2e-сценарии**. На примере Florence: версия v22 даёт `+20.3 п.п.` на ScreenSpot-V2, но **`−14 п.п.` pass rate в Magnitude** относительно v1 (84% → 70%). **Падение v22 на Magnitude при росте на ScreenSpot-V2 показывает что оптимизация под бенчмарк-метрики не транслируется в production-надёжность.** Это обосновывает построение собственного датасета вокруг паттернов реальных тестов вместо погони за бенчмарк-метриками.

## 1. Постановка задачи

### 1.1. GUI Grounding

**GUI Grounding** — задача локализации интерактивного элемента на скриншоте веб-страницы по естественно-языковой инструкции.

**Вход:**
- Скриншот веб-страницы (PNG, разрешение от 960×540 до 2560×1440)
- Текстовая инструкция типа `"create a new project"`, `"sign out"`, `"book 21:00 on the terrace"`

**Выход:**
- Координата клика `(x, y)` в нормализованных `[0, 1]`

### 1.2. Бенчмарк grounding'а ≠ реальное e2e-тестирование

Бенчмарки вроде **ScreenSpot-V2 / WebClick** измеряют «угадай координату с одного раза по картинке»: одна картинка + одна инструкция → одна координата → попал в bbox или нет. **Magnitude e2e** измеряет «реально пройди тест на живом сайте, агент может пробовать пока не получится».

**Конкретный пример: задача «Залогинься в GitHub».**

На бенчмарке (single-shot grounding):
- Дают **один скриншот** GitHub login page
- Дают **одну инструкцию** `"click sign in button"`
- Модель возвращает **одну координату**
- Попала в bbox → +1 hit. Промахнулась → 0.
- Финальная метрика: % попаданий по 437 web-сэмплам

В Magnitude e2e (multi-step task):
- Тест: «Залогинься в GitHub под учёткой X»
- LLM-агент ведёт сценарий пошагово на живом браузере:
  1. Открыть github.com → скриншот → grounding-модель ищет "Sign in" → клик
  2. Скриншот → ищет поле "Username" → ввод
  3. Скриншот → ищет "Password" → ввод
  4. Скриншот → ищет submit-кнопку → клик
  5. Скриншот → проверка что в header'е появился username (← evidence-of-completion)
- Если шаг сломался — агент **пробует снова**: переформулирует, скроллит, делает новый скриншот (← retry)
- **Тест пройден**, если в итоге залогинился. Не важно с какой попытки.

**Почему модель может выиграть на бенчмарке, но проиграть в e2e:**

1. **One-shot vs multi-shot.** Бенчмарк ловит ОДИН промах сразу. В e2e агент имеет 3-5 попыток на каждый клик через retry — точная но хрупкая модель проседает там, где «средняя но стабильная» работает.
2. **Узкое vs широкое распределение.** Бенчмарк собран по специальной разметке (сэмплы похожи). Real GitHub/BBC/Etsy отличаются по вёрстке, шрифтам, динамическому контенту — модель должна быть устойчива к разнообразию.
3. **Pixel-точность vs robustness.** Бенчмарк требует попасть строго в bbox. В e2e достаточно попасть достаточно близко чтобы агент мог продолжить — даже промах на соседний пиксель часто срабатывает из-за hover-эффектов и большой кликабельной зоны.

**Канонический кейс из этой работы (Florence v1 → v22, оба замера в едином пайплайне):**

| Замер | v1 | v22 | Δ |
|---|---|---|---|
| ScreenSpot-V2 web (n=437) | 20.4% | 40.7% | **+20.3 п.п.** на бенчмарке |
| Khabner ec637966 in-domain (n=1869) | 80.2% | 72.3% | −7.9 п.п. на in-domain |
| Magnitude e2e pass rate (n=50) | 84% | 70% | **−14 п.п.** на реальных тестах |

v22 расширили обучающую выборку под бенчмарк-метрики (ScreenSpot-V2 действительно вырос на +20.3 п.п.), но на out-of-distribution сайтах (BBC, Etsy, Stack Overflow) v22 стала хрупче — научилась узкому распределению ценой robustness. Регрессия на Magnitude e2e и на собственном ec637966 in-domain тесте подтверждает: бенчмарк-оптимизация не транслируется в реальное e2e-качество.

### 1.3. Метрика ClickAcc (для offline-замеров)

Стандартный SeeClick / ScreenSpot протокол: предсказание корректно если точка `(x, y)` лежит внутри ground-truth bounding box `[x_min, y_min, x_max, y_max]`. Координаты нормализованы `[0, 1]`. Failed parse (модель не вернула координаты) → counts as miss.

В Magnitude e2e соответствующая метрика — **soft-criterion pass rate**: тест считается пройденным, если хотя бы один прогон завершился без признаков галлюцинации `task:done`.

## 2. Методология эксперимента

### 2.1. Дообучение

**Контекст выбора Moondream2.** На момент начала работы (середина 2025) Magnitude использовала двухмодельную архитектуру: **Planner** (Gemini 2.5 Pro / Claude / GPT-4o) + **Executor** (Moondream2 через `MOONDREAM_API_KEY`). Этот выбор и определил Moondream2 как стартовую базовую модель настоящего исследования. В более поздних версиях (2026) Magnitude отказалась от компактного executor'а в пользу одной большой grounded-модели (Claude Sonnet 4 или Qwen2.5-VL 72B). Эта эволюция параллельна, а не альтернативна нашему подходу: переход на Claude/Qwen-72B упирается в экономические (×100 на запрос против fine-tuned Moondream — см. §6.5) и регуляторные (152-ФЗ, Указ №250 — см. §6.4) ограничения, при этом не решая исходной проблемы — общие модели не оптимизированы под паттерны e2e-тестирования (§5). Наш вклад — показать, что **компактный executor может догнать большой при правильно построенном датасете и LoRA-fine-tuning**, оставаясь при этом on-prem-deployable.

**Архитектуры моделей:**

| Модель | Параметры | Архитектура | Базовая способность |
|---|---|---|---|
| Moondream2 base | 1.86B | ViT + LM (vikhyatk) | Имеет встроенный pointing variant (через `model.point()` API) |
| Florence-2-base | 232M | DaViT + BART (microsoft/Florence-2-base-ft) | Token-level grounding `<loc_X1><loc_Y1>...` |
| Florence-2-large | 770M | DaViT + BART (microsoft/Florence-2-large-ft) | То же, увеличенный vision encoder |

**Метод адаптации:** LoRA (Hu et al., 2022).
- Изменяет менее 2% параметров
- Финальные конфигурации (v22): тестированы оба варианта `r=8, alpha=16` и `r=4, alpha=8`, `coord_decoder` заморожен (для Moondream); `r=8` — production recommendation (best на ScreenSpot-V2 web 73.9% vs 73.7% у `r=4`, см. §4.4)
- LR = 1e-5 с cosine schedule, 3 эпохи
- Размер LoRA-адаптера (.pt / .safetensors): Moondream **v12 — 72 МБ** (содержит обучаемый coord_decoder), Moondream **v22 — 12 МБ** (coord_decoder заморожен, r=4); Florence-base — ~7 МБ; Florence-large — 18 МБ

**Эволюция рецепта** (10 итераций v12 → v22 на Moondream):

| Версия | Изменение | ScreenSpot-V1 |
|---|---|---|
| v12 | начальная (`r=16`, `coord_decoder` обучается) | 69.3% |
| v13 | freeze `coord_decoder` | 70.4% (+1.1) |
| v14 | LoRA rank 16 → 8 | 72.5% (+2.1) |
| v15 | rank 8 → 4 | 72.7% (+0.2) |
| v22 | + расширенная выборка, тюнинг LR | 79.4% / 79.7% на V2 |

**Ключевые находки рецепта:**
1. Freeze `coord_decoder` критичен — иначе catastrophic forgetting (на v12 LoRA теряла -7 п.п. vs base на out-of-distribution).
2. Лучше **низкий rank** (r=4) при широких данных, чем высокий rank на узких.

### 2.2. Датасет: e2e-driven construction (`Khabner/moondream-data`)

**Принципиальное решение:** датасет строился **под паттерны реального e2e-тестирования**, а не под улучшение бенчмарк-метрик.

- **18 694 примера** (train 14 956 / val 1 869 / test 1 869) в первой публикации (revision `ec637966`); расширен до 21 832 в более поздней (revision `ba10ae2b`)
- Источники:
  - **900 синтетических страниц** — HTML-шаблоны с 67 вариантов 15 типов секций, эмулирующих типичные e2e-сценарии (формы, табы, аккордеоны, navigation bars, calendar pickers и т.д.)
  - **29 скрапленных production-сайтов** — Apple, HuggingFace, MDN, Stripe, Vercel, Linear, GitLab, Wikipedia и др.
  - **9 ручных разметок** — Amazon, Netflix, TikTok, Twitch, McDonald's и др.
- **Y-axis балансировка** против перекоса в верхнюю часть страницы
- **English-only** (ограничение Moondream2)

**Распределение по типам элементов:** ориентировано под реальное e2e-тестирование — преобладают button (33.8%), link (29.1%), menu_item (11.1%) — то с чем агент сталкивается в production-задачах.

**Failure-driven итеративная аугментация (научная новизна):** цикл из 9 итераций (v0 → v9). Каждая итерация: (1) парсинг новых production-сайтов и добавление их в датасет, (2) обучение новой версии LoRA, (3) **offline grounding на in-domain test** (Khabner held-out) — анализ категорий, на которых модель ошибается чаще всего, (4) **генерация синтетических HTML-секций под выявленные слабые категории** (например, «icon miss = 17%» → добавление `icon_controls` с 23 вариантами), (5) добавление синтетики в датасет → следующая итерация. Magnitude e2e использовался только в финале для валидации, не как обратная связь между итерациями.

| # | Триггер | Источник | Добавлено |
|---|---|---|---|
| 0 | стартовая инфраструктура | — | scraper + 10 site parsers |
| 1 | низкое разнообразие датасета | manual review | generator с 6 базовыми секциями |
| 2 | ошибки парсинга collision/store badges | offline grounding | secs `collision`, `store_badges` |
| 3 | gaming UIs не покрыты | use-case (Roblox) | `thumbnail_grid` (5 layouts) |
| 4 | provider tabs не покрыты | use-case (BrowserStack) | `labeled_controls` (8 вариантов) |
| 5 | checkbox miss = 1.6% | offline grounding | `checkbox_group` (8 вариантов) |
| 6 | icon miss = 17% | offline grounding | `icon_controls` (3 волны, 23 варианта) |
| 7 | "at top/bottom" miss = 44% | offline grounding | `repeated_cta` (3 варианта) |
| 8 | inline links miss = 15% | offline grounding | `text_links` (4 варианта) |
| 9 | v11 error breakdown | offline grounding | 10 точечных доработок |

### 2.3. Почему мы намеренно не оптимизировали под ScreenSpot/WebClick

**Изначально v12 LoRA на Moondream при сборе датасета под e2e-паттерны давала всего 69.3% на ScreenSpot-V1** — модель не оптимизировалась под этот бенчмарк. При расширении выборки (v22) с прицелом на бенчмарк-числа общая ScreenSpot-метрика выросла до 79.4%, но **Magnitude e2e показал регрессию** на ряде категорий (см. § 5). Поэтому стандартные бенчмарки в этой работе используются для **позиционирования наших моделей в системе координат литературы** (где мы относительно UGround / Holo1 / Qwen2.5-VL), а не как основное мерило отбора production-чекпойнта.

**Основной (production-grade):**

| Бенчмарк | Описание | Размер |
|---|---|---|
| **Magnitude e2e** | 50 тестов на ~25 публичных сайтах через `magnitude-test@0.2.21` с Claude Sonnet 4.6 как агентом | 50 |

**Дополнительные (offline grounding):**

| Бенчмарк | Источник | Размер | Web subset |
|---|---|---|---|
| **Khabner held-out** (in-domain) | Khabner/moondream-data, revision `ec637966` | 1 869 | 100% |
| **Khabner held-out v22** (in-domain) | Khabner/moondream-data, revision `ba10ae2b` | 2 183 | 100% |

⚠️ **Caveat:** ScreenSpot-V2 / WebClick — это **single-shot GUI grounding-бенчмарки** (one screenshot → one instruction → one coordinate → hit/miss); они не моделируют multi-step retry и assertion-проверки реального e2e-тестирования. Используются для позиционирования среди literature; основной критерий отбора моделей — Magnitude e2e.

**Позиционирование в литературе.** ScreenSpot-V2 / WebClick дают возможность увидеть где наши модели стоят на общепринятой шкале: наш Moondream2-base даёт 79.7% на ScreenSpot-V2 overall — это сопоставимо с другими open-моделями ~2B-класса (UGround-V1-2B literature: 79.31%, Δ +0.4 п.п. в пределах шума). То есть наш пайплайн измерения работает в рамках общепринятых норм, а наши open-модели играют в той же лиге, что mainstream литература. Эти бенчмарки **не используются как критерий отбора production-чекпойнта** (этот критерий — Magnitude e2e, §4.1).

## 4. Результаты

### 4.1. Magnitude End-to-End Validation (основной бенчмарк)

**Конфигурация:** runner = `magnitude-test@0.2.21`, viewport 1200×800. 50 тестов на mainstream-сайтах (dev, media, travel, e-commerce, social, reference).

В роли **LLM-агента (reasoning)** использовался Claude Sonnet 4.6 через `api.vsellm.ru`. Выбор обоснован практическими соображениями: исследование велось на локальной машине, и для возможности **визуально проверять правильность прохождения каждого теста** (наблюдать клики агента в реальном времени, анализировать action-логи) удобнее опираться на стабильный API, чем поднимать локальную reasoning-модель уровня Qwen2.5-72B и поддерживать её inference. **Grounding-модели (наш Moondream/Florence + LoRA) при этом запускались локально на MacBook с Apple M1 — именно их качество и тестировалось.** 

⚠️ **Важная оговорка:** в этой архитектуре Claude **не является grounding-моделью** — он только декомпозирует задачу на шаги и решает «что делать дальше». Координаты клика на каждом шаге предсказывает наша компактная open-модель. То есть Claude в Magnitude и Claude в офлайн grounding-таблицах (§4.4-4.5) — это **разные роли** одной модели.

## 5. Главная методологическая находка: Bench scores ≠ E2E quality

**Florence v1 → v22 — каноничный случай benchmark→e2e transfer gap.** Все три замера ниже сделаны в едином пайплайне (ClickAcc, point-in-bbox, нормализованные координаты `[0, 1]`):

| Замер | F-v1 | F-v22 | Δ | Выборка |
|---|---|---|---|---|
| Khabner ec637966 ClickAcc (in-domain для v1) | 80.2% | 72.3% | **−7.9 п.п.** | n=1 869 |
| **ScreenSpot-V2 web** | **20.4%** | **40.7%** | **+20.3 п.п.** | n=437 |
| **Magnitude e2e pass rate** | **84%** | **70%** | **−14 п.п.** | n=50 |

**Интерпретация:**
- v22 расширяла обучающую выборку с прицелом на бенчмарк-метрики → **выросло на ScreenSpot-V2 (+20.3 п.п.)**
- На in-domain ec637966 (тест-сплит датасета v1) **v22 ХУЖЕ v1 на 7.9 п.п.** — это уже out-of-domain для v22 (она обучалась на ba10ae2), и расширение не транслируется обратно
- На out-of-distribution e2e сайтах (BBC, ESPN, Booking, Etsy, Wikipedia, Stack Overflow и т.д.) — **регрессия −14 п.п. pass rate**
- 9 конкретных регрессий между v1 и v22 (verbatim из Magnitude run-логов): #4 Facebook Photos, #8 DemoQA Email, #17 MDN map sidebar, #23 Weather 5th day, #29 YouTube 3rd video, #31 SO `react` tag, #33 Russia row, #34 Beyoncé `[25]` reference, #43 GitHub Email label
- Это **классический overfitting на narrow distribution**: модель оптимизировалась под структуру бенчмарк-сэмплов, потеряла robustness на разнообразии production-вёрстки

**Вывод:** при разработке моделей для деплоя в e2e-тестирование следует **валидировать на e2e harness'е** (как Magnitude), а не только на single-shot grounding-бенчмарках. ScreenSpot/WebClick полезны для калибровки против литературы, но **не должны быть единственным критерием отбора чекпоинта** — в нашем кейсе оптимизация под бенчмарк-метрики стоила 14 п.п. реального e2e pass rate **и** 7.9 п.п. на собственном in-domain тесте более ранней ревизии данных.

## 6. Сравнение качество/цена

**Методологические допущения.** Все стоимостные расчёты приведены на 7 мая 2026 при курсе ЦБ 75 ₽/\$ (фактически 75.2246 ₽/\$ на дату). Аренда GPU — публичные тарифы российских провайдеров: RTX 4090 ~95 ₽/час (immers.cloud, AdminVPS), Tesla T4 / NVIDIA A2 ~25 ₽/час (Selectel, immers.cloud)¹, H100 80 ГБ ~350 ₽/час (intelion.cloud, K2 Cloud). Прайсы API — официальные ставки провайдеров за 1M токенов: GPT-4o \$2.50 / \$10 (input/output), Claude Sonnet 4.6 \$3 / \$15, Gemini 2.5 Pro \$1.25 / \$10 (≤200K context). Российские пользователи получают доступ к API через посредников типа vsegpt.ru с типичной наценкой 15–25%, что отражено в таблицах двойными значениями. Утилизация GPU при single-shot inference принята 30% — реалистичное значение для interactive workload без агрессивного батчинга.

¹ Опубликованные ставки на 2026-05-07: **immers.cloud Tesla T4** — от 19.61 ₽/час (минимальная single-T4 конфа `teslat4-1.4.8.60`); **immers.cloud NVIDIA A2** — от 21.38 ₽/час (`teslaa2-1.4.8.60`) или 22.95 ₽/час (`teslaa2-1.4.16.120`, 16 GB RAM); **Selectel Tesla T4** — 39.17 ₽/час standard / 11.75 ₽/час preemptible. **На 2026-05-07 T4 на immers.cloud была временно недоступна, поэтому эмпирическая валидация (§6.1) проведена на NVIDIA A2 при 22.9 ₽/час** (`teslaa2-1.4.16.120`).

**Минимально достаточное железо.** Дообученные Moondream2 (1.86 млрд параметров) и Florence-2 (0.23–0.77 млрд) в FP16 требуют 4–6 ГБ и 1–3 ГБ VRAM соответственно — на порядок меньше типового datacenter inference-GPU (A100/H100, 40–80 ГБ). Это позволяет разворачивать систему на бюджетных Tesla T4 / NVIDIA A2 (16 ГБ VRAM) или RTX A2000.

**Роль каждой платформы в исследовании:**

| Платформа | Использование | Что измерялось |
|---|---|---|
| **MacBook M1 / MPS** | Magnitude e2e (§4.1) — все 50 тестов с grounding-моделью локально | **Качество** в production-сценарии (pass rate, e2e) |
| **NVIDIA A2 (immers.cloud)** | Эмпирический замер latency для production cost (§6.1) | **Стоимость** на бюджетной карте — 0.017 ₽/запрос |
| **RTX 4090 (immers.cloud)** | Дообучение LoRA + offline grounding-бенчмарки (§4.2-4.5) | Reference-latency для расчётов; secondary cost baseline |

**4090 — не production target**, а measurement reference: на ней мы уже арендовали GPU для обучения и offline-бенчмарков, поэтому там же сняли latency. Реалистичный production deployment — A2 / T4 (дешевле, latency приемлема) или M1 (CI на дешёвом потребительском железе). Ключевой экономический аргумент работы — **отсутствие требования к премиум-железу**: модель работает и на M1 для интерактивного debug, и на бюджетной A2 / T4 для серверного inference.

### 6.1. Стоимость одного запроса grounding

Запрос к VLM представляет собой single-shot inference: на вход — скриншот веб-страницы (1500–2700 image-токенов в зависимости от разрешения и режима detail) и краткий текстовый промпт, на выход — координаты целевого элемента (~20 токенов). Формула стоимости для on-prem варианта:

`C_request = GPU_rate (₽/ч) × latency (с) / (3600 × utilization)`

Для API: `C_request = (T_in × p_in + T_out × p_out) / 10⁶ × курс`.

| Модель | Latency на NVIDIA A2 (с)³ | ₽/запрос (direct) | Через рос. посредника |
|---|---|---|---|
| **Moondream + LoRA v12** | **0.800** | **0.017** | — |
| **Florence-base + LoRA v22** | **0.428** | **0.0091** | — |
| Florence-large + LoRA v22 | 1.165 | 0.025 | — |
| GPT-4o | — | **0.16** | **~0.20** |
| Claude Sonnet 4.6 | — | **0.27** | **~0.32** |
| Gemini 2.5 Pro² | — | **0.26** | **~0.31** |

² С учётом thinking budget ~250 токенов; без thinking — 0.07 ₽ direct.
³ Методология замера latency: 30 timed inferences после 3 warmup на синтетических 1280×720 RGB скриншотах, immers.cloud `teslaa2-1.4.16.120` (см. `results/a2_latency.json`).

**Допущения для API-моделей.** Single-shot grounding-запрос: один screenshot 1024×768 в `detail: "high"` + короткий промпт (~30 токенов) + 20 output-токенов. Image-токены считаются по официальной формуле каждого провайдера:

- **GPT-4o**: tile-based по [docs OpenAI](https://platform.openai.com/docs/guides/vision/calculating-costs) — `85 + 170 × tiles`. Для 1024×768 с тайлами 512×512: `ceil(1024/512) × ceil(768/512) = 2 × 2 = 4` тайла → **765 image-токенов**.
- **Claude Sonnet 4.6**: формула Anthropic `tokens ≈ width × height / 750`. Для 1024×768: 786 432 / 750 ≈ **1 050 image-токенов**.
- **Gemini 2.5 Pro**: тайловый подход `258 tokens × ceil(w/768) × ceil(h/768)`. Для 1024×768: 258 × 2 × 1 = **516 image-токенов** (≈600 с overhead).

Если в production используются длинные системные промпты + few-shot примеры, реальный input будет выше — для baseline-сравнения берётся минимально достаточный single-shot grounding-запрос.

**Эмпирическая валидация на NVIDIA A2.** Замер на immers.cloud `teslaa2-1.4.16.120` (22.9 ₽/час) подтверждает, что бюджетная инференс-карта класса A2 / Tesla T4 даёт грошовую стоимость per-request (0.009–0.025 ₽) для всех трёх размеров наших моделей. Latency умеренная за счёт Ampere FP16-tensor cores, частично компенсирующих узкую память (200 ГБ/с) на compute-bound частях (attention/MLP). Это **снимает caveat «future work»** для T4-класса карт и подтверждает headline-аргумент работы про **отсутствие требования к премиум-железу**.

**Ключевой вывод §6.1.** Дообученные компактные VLM на бюджетной NVIDIA A2 (~0.009–0.025 ₽/запрос) в **×12–19 дешевле** проприетарных API через российского посредника (~0.20–0.32 ₽/запрос). Среди open-моделей наши LoRA примерно **в ×8 дешевле** OS-Atlas-7B (~0.14 ₽/запрос на эквивалентном железе) за счёт меньшего размера. Качественный аргумент (acc@2% 84.4% для Moondream-LoRA против 80.8% для Florence-LoRA против 69% для Moondream-base) усиливается экономическим — наша конфигурация Парето-доминирует все альтернативы по совокупности качество × стоимость.

### 6.3. Окупаемость дообучения

Для коммерческой адаптации метода (с использованием опубликованных в работе моделей и датасета Khabner/moondream-data) учитываются: GPU-время на обучение под целевой домен (~30 часов на RTX 4090, ~2 850 ₽), инженерное время — адаптация датасета под специфику UI заказчика, валидация, интеграция в CI-пайплайн (~80–120 часов senior ML-инженера при ставке 2 500–3 500 ₽/час), плюс инфраструктурные накладные.

| Параметр | Значение |
|---|---|
| Стоимость дообучения (GPU + engineering) | 200 000–300 000 ₽ единоразово (для коммерческой адаптации); ~0 в академической среде |
| Объём тестирования (продуктовая компания со зрелым QA-процессом⁴) | 100 000 запросов/мес |
| Минимально достаточный GPU | 1× NVIDIA A2 (22.9 ₽/час, 16 ГБ VRAM, эмпирически проверено — §6.1)⁵ — пропускная способность ~1 350 запросов/час при 30% утилизации (Moondream + LoRA, latency 0.80 с). Это покрывает peak-нагрузку 100k запросов/мес ≈ 970 req/час (если concentrated в business-hours: 5 дней × 22 рабочих дня × ~1 ч/день пика); 24/7-average нагрузка — лишь ~139 req/час (100k ÷ 720 ч) |
| Затраты при API (GPT-4o через рос. посредника) | ~62 000 ₽/мес |
| Затраты на on-prem (Moondream LoRA на NVIDIA A2)⁶ | ~16 500 ₽/мес (24×7 dedicated rental) |
| **Экономия** | **~45 500 ₽/мес (73%)** |
| **Окупаемость** | **4–7 месяцев** (200 000 ÷ 45 500 ≈ 4.4; 300 000 ÷ 45 500 ≈ 6.6) |

⁴ Сценарий: команда из 5 QA-инженеров, ~1 000 e2e-тестов в неделю при ~25 grounding-вызовах на тест.
⁵ Tesla T4 на immers.cloud в момент проведения замеров была недоступна; A2 — следующий эквивалент по классу (16 GB VRAM, low-power Ampere, ~22.9 ₽/час). При наличии T4 цифры могут быть несколько лучше: T4 на 320 ГБ/с bandwidth (vs A2 200 ГБ/с) и при тарифе 19.6 ₽/час ожидаемо даёт latency ~0.5 с на Moondream + LoRA, итого ~0.009 ₽/запрос (19.6 × 0.5 ÷ 3600 ÷ 0.30).
⁶ При 24×7 dedicated rental A2 (22.9 ₽/ч × 720 ч ≈ 16 500 ₽/мес) переменные затраты доминируют независимо от объёма; при использовании serverless inference или shared GPU фактическая стоимость снижается до маргинальных ~1 700 ₽/мес (100k × 0.017 ₽).

**Масштабирование.** При объёме 1 млн запросов/мес окупаемость <2 месяцев. Среднесуточная нагрузка ≈ 1 389 запросов/ч (1M ÷ 720 ч); пропускная способность одной T4 при 30% утилизации (Moondream LoRA, проекция 0.5 с) ≈ 2 160 запросов/ч — fits с запасом (~14 000 ₽/мес). Одна A2 (измеренная latency 0.8 с, ~1 350 запросов/ч при 30%) на пиках 1M/мес уже на пределе — нужна либо вторая A2, либо повышение утилизации до 50% (~2 250 запросов/ч), либо переход на T4. Свыше ~10 млн запросов/мес — горизонтальное масштабирование (несколько T4) или одна RTX 4090 для плотности инференса.

### 6.4. Регуляторный аргумент

Для регулируемых отраслей проприетарный API не является легитимной альтернативой в принципе:

**Финансовый сектор.** 161-ФЗ «О национальной платёжной системе» и 395-1-ФЗ «О банках и банковской деятельности» ограничивают передачу банковской тайны и платёжных данных третьим лицам, особенно нерезидентам. Даже для тестовых сред с обезличенными данными передача структуры UI с реквизитами и идентификаторами счетов может трактоваться как раскрытие.

**Здравоохранение.** 323-ФЗ «Об охране здоровья граждан Российской Федерации» совместно со 152-ФЗ запрещают передачу врачебной тайны и медицинских персональных данных во внешние сервисы без явного согласия пациента.

**Персональные данные (общий случай).** 152-ФЗ «О персональных данных» требует размещения операций обработки и хранения ПД на территории РФ (поправки 2014 года, ст. 18 ч. 5; усилены 23-ФЗ от 28.02.2025, в силу с 01.07.2025). Использование cloud API западных провайдеров для тестирования интерфейсов, где скриншоты содержат пользовательские данные, представляет прямое нарушение.

**Государственный сектор и КИИ.** Постановление Правительства РФ №1236 от 16.11.2015 устанавливает приоритет отечественного ПО при государственных и муниципальных закупках (44-ФЗ / 223-ФЗ); 187-ФЗ от 26.07.2017 «О безопасности критической информационной инфраструктуры» и Указ Президента РФ №250 от 01.05.2022 «О дополнительных мерах по обеспечению информационной безопасности» (с 01.01.2025 — запрет иностранных средств защиты информации) — для субъектов КИИ.

В таких сценариях on-prem решение становится **единственно легитимной опцией**. База экономического сравнения смещается с «API vs on-prem» на «on-prem AI vs ручное тестирование QA-инженером»: при ставке 1 500 ₽/час QA-специалиста даже 1 000 grounding-операций в месяц окупают on-prem решение за 1–2 рабочих дня.

### 6.5. Полная стоимость e2e-тестирования (reasoning + grounding)

Расчёты §6.1–6.3 покрывают только grounding-этап. Реальная Magnitude-архитектура требует также reasoning LLM-агента, декомпозирующего задачу на шаги. Если reasoning = Claude API, то для compliance-сценариев это решение неприменимо: данные продолжают передаваться во внешний сервис.

**Per-test breakdown (7 turns):**

| Компонент | Hardware / Provider | Стоимость, ₽/тест |
|---|---|---|
| Claude Sonnet 4.6 reasoning, без кэша⁷ | API (direct \$3/\$15 per 1M) | ~20.5 (direct) / ~24.6 (рос. посредник) |
| Claude Sonnet 4.6 reasoning, с prompt caching | API | ~5–7 |
| Qwen2.5-72B local reasoning⁸ | 1× H100 80 ГБ | зависит от объёма (см. ниже) |
| Moondream/Florence + LoRA grounding | 1× A2 (production) | ~0.12 (7 turns × 0.017) |
| Claude grounding (closed-only baseline) | API | ~1.9 (direct) / ~2.3 (посредник) |

⁷ Расчёт: при линейном росте контекста по turn'ам суммарный input ~84К токенов (7 turns × ~12К средний), output ~1.4К токенов.
⁸ Throughput Qwen-72B на H100 ~50 tok/s с vLLM-оптимизациями; 7 turns × 200 output tokens = ~28 секунд GPU-времени.

**Сценарии при dedicated rental (₽/test):**

| Архитектура | 1k тестов/мес | 10k тестов/мес | 100k тестов/мес |
|---|---|---|---|
| Closed-only (Claude reasoning + Claude grounding, посредник) | ~27 | ~27 | ~27 |
| Hybrid (Claude reasoning + LoRA grounding) | ~25–43⁹ | ~26 | ~25 |
| Hybrid c prompt caching | ~7–25⁹ | ~8 | ~7 |
| **Fully open (Qwen-72B/H100 + LoRA)** | ~270¹⁰ | ~27 | **~3** |

⁹ Диапазон: маргинальная стоимость на shared/serverless GPU vs 24×7 dedicated rental A2.
¹⁰ При малом объёме H100 idle большую часть времени, фикс-стоимость аренды доминирует. Точка безубыточности fully-open vs closed-only — ~9–12k тестов/мес.

**Месячная стоимость (10k тестов/мес, dedicated rental):**

| Архитектура | Reasoning | Grounding | **Итого/мес** |
|---|---|---|---|
| Closed-only | ~250 000 ₽ | ~23 000 ₽ | **~273 000** |
| Hybrid | ~250 000 ₽ | ~16 500 ₽ | **~267 000** |
| Hybrid c prompt caching | ~60 000 ₽ | ~16 500 ₽ | **~77 000** |
| **Fully open** | ~252 000 ₽¹¹ | ~16 500 ₽ | **~269 000** |

¹¹ H100 24×7 dedicated при 10.8% utilization. При serverless billing (пайюзеджу): ~30 000 ₽/мес → fully open суммарно ~50 000 ₽/мес.

**При 100k тестов/мес** fully-open в **~10× дешевле** closed-only за счёт высокой утилизации H100. При <10k тестов/мес fully-open экономически нецелесообразен без compliance-требований — H100 простаивает.

**Компромиссы по сценариям.** Compliance-отрасли (банк, медицина, госсектор) — fully open является единственной легитимной опцией; экономика сравнивается не с API, а с человеко-часами QA-инженера. Высокий объём тестирования (>10k тестов/мес) — fully open в 10–11× дешевле closed-only при 100k+ тестах/мес. Низкий объём без compliance-требований (≤10k тестов/мес) — рекомендуется hybrid (Claude reasoning + LoRA grounding) c prompt caching: экономия ~70% против closed-only без необходимости развёртывания H100-инфраструктуры.

⚠️ **Caveat.** Числа Qwen-72B reasoning — расчётные оценки на основе публичных throughput-замеров vLLM; в Magnitude pipeline эта конфигурация не запускалась. Эмпирическая валидация на open-source reasoning моделях — направление future work.

### 6.6. Чувствительность к курсу и аппаратной платформе

При колебаниях USD/RUB в диапазоне 70–90 ₽/\$ стоимость API-вариантов меняется пропорционально (±20% от базы), стоимость on-prem не изменяется (тарифы российских GPU-провайдеров номинированы в рублях). Это формирует дополнительный экономический аргумент в пользу on-prem решения как защиты от валютного риска: при ослаблении рубля экономия от перехода на on-prem только растёт.

Рост цен на H100 (зафиксированный SemiAnalysis рост на ~40% за период октябрь 2025 – март 2026) ухудшает экономику fully-open сценария на 15–25% при dedicated rental, но не затрагивает grounding-компонент: NVIDIA A2 / Tesla T4 / RTX A2000 — массовые бюджетные карты со стабильным предложением на российском рынке. Это формирует **robust нижнюю границу** экономической эффективности предложенного метода: даже при дальнейшем удорожании datacenter-GPU grounding-stage остаётся в ×12–19 дешевле API (см. §6.1).

**Низкий барьер входа по железу.** Production-нагрузка работает на инференс-оптимизированных картах класса A2 / Tesla T4 (~21–25 ₽/час, эмпирически проверено на A2 в §6.1) с per-request cost 0.009–0.025 ₽. Tesla T4 в low-profile форм-факторе (~\$2 000 на вторичном рынке РФ) делает on-prem решение реалистичным для небольших организаций без капитальных AI-бюджетов — ключевой аргумент в контексте democratization of AI через open-модели, не требующие премиум-инфраструктуры.

## 7. Выводы

### 7.1. Подтверждение гипотезы

**Production-сценарий (Magnitude e2e):**
- Moondream2 + LoRA v12 — **96% pass rate** на 50 реальных тестах (vs base 88%, +8 п.п.)
- Florence-2-base + LoRA v1 — 84% при 232M параметров
- Прирост LoRA проявляется на category-targeted тестах (TAG/CHECKBOX/LABEL/BUTTON), где offline `acc@2%` предсказывал разрыв

**Offline grounding (ec637966 held-out):**
- LoRA на Moondream — `+15.4 п.п. acc@2%` (69.0% → 84.4%)
- LoRA на Florence-2 — `+78.2 п.п. acc@2%` (2.6% → 80.8%)

**Стандартные бенчмарки** (контекстная калибровка):
- Moondream-base 79.7% on V2 ≈ UGround-V1-2B 79.31% (literature) — пайплайн валиден
- Florence-LoRA даёт +73.7 п.п. с почти-нуля на Khabner v22 test — самый сильный прирост от LoRA

**Экономическая часть:**
- Стоимость grounding-запроса: **~0.017 ₽ на NVIDIA A2** (эмпирически замерено) vs ~0.20 ₽ за GPT-4o через посредника — **×12 экономия**; vs Claude/Gemini посредник (~0.31–0.32 ₽) — ×18–19
- Полная стоимость e2e-теста (reasoning + grounding) с prompt caching: ~7 ₽ vs ~30 ₽ closed-only — экономия ~70%
- Окупаемость коммерческой адаптации: 4–7 месяцев при 100k запросов/мес
- Регуляторная значимость для compliance-отраслей (банк, медицина, госсектор)

### 7.2. Научная новизна

1. **E2E-aware dataset construction с failure-driven итеративной аугментацией** — методика построения датасета вокруг паттернов реального e2e-тестирования (формы, табы, аккордеоны, чекбоксы, inline-ссылки, footer-CTA и т.д.), а не вокруг готовых grounding-бенчмарков. Цикл из 9 итераций (67 синтетических секций), где обратная связь шла от **offline grounding-ошибок на in-domain test**: на каждом шаге анализировались категории с высоким miss-rate, и под них генерировались целевые синтетические HTML-шаблоны. Magnitude e2e использовался только в финале для валидации (не как feedback-loop), что снимает риск overfitting'а на e2e-выборку.
2. **Empirical demonstration of benchmark→e2e transfer gap** — на примере Florence v1 → v22: `+20.3 п.п.` ScreenSpot-V2 / `−7.9 п.п.` ec637966 in-domain ClickAcc / `−14 п.п.` Magnitude e2e pass rate. Методологический вклад: показано что нельзя оптимизировать модель под grounding-бенчмарки если цель — production e2e тестирование.
3. **Magnitude как evaluation harness** для grounding-моделей в реальном UI-testing сценарии. 50 тестов на 25 mainstream-сайтах с category-targeted purposeful selection.
4. **Multi-benchmark evaluation infrastructure** с найденными артефактами closed-API:
   - Claude image-scaling artifact (`>1568px` ресайз ломает координатный фрейм; ×40 разница в ClickAcc между бенчмарками)
   - Gemini native 0-1000 coordinate scale (×9 разница в парсинге)
   - Закрытые API в raw-prompt сильно ниже их published numbers (которые часто получены с harness'ами типа Computer Use API, Set-of-Mark, Iterative Narrowing)
5. **Первое систематическое raw-prompt сравнение** GPT-4o, Claude Sonnet 4.6 и Gemini 2.5 Pro как grounding-моделей на ScreenSpot-V2, WebClick и Khabner test одновременно (в Magnitude e2e closed-API не использовались как grounding — только Claude в роли reasoning-агента).

### 7.3. Ограничения

- **Один LLM-агент (reasoning).** Magnitude eval использует Claude Sonnet 4.6 как reasoning-агент по практическим причинам (стабильный API + возможность визуально верифицировать прогон). Реалистичнее всего полученные числа отражают сценарий «проприетарный reasoning + локальная on-prem grounding-модель». При замене reasoning на open-модель (Qwen2.5-72B, Llama-3.3-70B) поведение может отличаться — особенно на underspecified тестах (#15, #19) где Claude иногда галлюцинирует `task:done`. Это направление будущей работы.
- **50 тестов** — узкая выборка для строгой статистики; нужен больший корпус (250+) для расчёта доверительных интервалов
- **Florence-large v22 в Magnitude** покрывал только 11/50 тестов (partial coverage); не вошёл в финальное сравнение
- **Closed APIs тестированы без harness'ов** — числа с Computer Use / SoM / Iterative Narrowing могут существенно превышать наши
- **`task:done` галлюцинации Claude** на underspecified тестах (#15, #19) — частично mitigation через анализ action-логов

### 7.4. Рекомендация

**Moondream2 + LoRA v12 — production grounding-модель** для UI testing pipeline'а. Аргументы:
- 96% pass rate на 50 реальных e2e-тестах
- Median 52.2 с/тест
- Единственная модель со 100% pass rate на category-targeted Round 9 — 8/8 тестов (#37-44, HEADING/CHECKBOX/LABEL/BUTTON)
- **~0.017 ₽/grounding-запрос на бюджетной NVIDIA A2** (эмпирически замерено, см. §6.1); полностью on-prem; LoRA-адаптер 72 МБ поверх 1.86B base (Moondream v12)

Для compliance-сценариев (банк, медицина, госсектор) — единственная legitimate альтернатива проприетарным API.

### 7.5. Направления развития

1. Расширение Magnitude eval до 250+ тестов для строгой статистики
2. Сравнение с harness-augmented closed APIs (SoM, Iterative Narrowing, native Computer Use)
3. Адаптация на ScreenSpot-Pro (профессиональные UI: CAD, IDE)
4. Multi-agent evaluation (вариация LLM-агента)
